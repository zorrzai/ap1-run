# AP-1 Runner — System Build Specification

**Version 0.3 (draft) · 28 July 2026 · for internal and external technical review**

Document class: Engineering build specification — for the development team and
for external technical review.

System: a reference execution and scoring instrument for The Admissibility
Protocol. Model-, vendor- and domain-agnostic. Designed to be executed by a
third party, against a system ZORRZ has never seen, without
ZORRZ involvement.

Companion material: AP-1 v1.3 draft-for-comment (28 July 2026); Certanum —
System Build Specification v0.2.1; *Computational Provenance and Numerical
Admissibility* (technical note, July 2026).

**Alignment obligation.** Every contract here traces to a clause of **AP-1
v1.3 draft-for-comment dated 28 July 2026**, whose canonical hash is recorded
at seal time by R1.1 and reproduced in every report. An earlier v1.3 working
draft dated 25 July 2026 exists, uses different section numbering, and is
**retired** — it is not the referent of any clause cited here. Where an adopted
v1.3 differs from the 28 July draft, this specification is defective until
updated, and the standard governs.

### Changes from v0.2

- **R1.3 evidence classes rewritten.** v0.2 graded invocation evidence by
  richness and ranked a signed provenance token as strongest. The token is
  generated by the system under test about itself, so that reinstated the
  erratum's most serious defect inside the instrument built to prevent it.
  Evidence is now graded by **independence and verifiability**, and an
  unverified token ranks **below** a platform record. §5.
- **R0.4** (was R3.4 — a Layer 0 module numbered into Layer 3) gains a
  normative **numeric token grammar**.
- **R2.0** gains the lookup-collision rule, closing a RETRIEVED blind spot.
- **R2.2** reports the D2 mechanism class **per surface**, not per system.
- **R2.4** step 3 composes declared transformations with intermediates.
- **R0.1** enforces the standard's minimum-n rules at load.
- **R1.1** seals the AP-1 text version the run claims conformance to.
- **R3.3** names the inter-rater statistics.
- **§11** rewritten for **Certanum**, with the assessment-surface requirement.
- **§12.8** states the licence decision.

## 1. Purpose, and the one property that matters

AP-1 states that any party may run it without the author's involvement. That is
currently a claim. **This instrument exists to convert it into a fact.**

Every design decision serves two facts about the intended user:

1. They will run this against a system inside their own perimeter.
2. Their information-security function will read the code before that happens.

A dependency they cannot audit, a network call they did not expect, or a
scoring rule they cannot follow is each sufficient to stop the run. The
instrument is therefore small, legible, and boring by design.

### 1.1 What the runner measures

| Dimension | Automated | Mechanism |
|---|---|---|
| D1 accuracy | Partially — R2.0 | Comparison to a computed expected value; ambiguous cases adjudicated |
| D2 reproducibility | Yes | Repeat execution; per-surface mechanism classification; parameter-echo verification |
| D7.1 invocation | Yes | Structural record, graded by evidence class |
| **D7.2 operand provenance** | **Yes** | **Tool arguments resolved against source fields and reference intermediates** |
| D7.3 transcription | Yes | Tool return value compared to released figure |
| D3, D4, D5, D6 | No | Human adjudication |

**D7.2 is the distinguishing measurement and the reason this is not an
observability tool.** Tool-call tracing is widely available. Resolving each
operand against the source values and legitimate intermediates of a reference
derivation is not.

### 1.2 Non-goals — stated so they are not added later

- **No language model anywhere.** Not in question generation, expected-value
  construction, scoring, figure identification, or reporting.
- **No automation of D3–D6.** AP-1 §13.1 requires transcript-level human
  adjudication on every dimension.
- **No inference of an answer where the evidence is ambiguous.** The runner
  never guesses.
- **No telemetry, analytics, or phone-home of any kind.**
- **No scoring of a system the runner also configures.**

## 2. Architecture

Two passes, four layers, one immutable artifact between them.

```
   config.yaml + fixture + question set + ground-truth module
                            |
                    +-------v--------+
                    |  R1  EXECUTE   |   no scoring occurs here
                    +-------+--------+
                            |
                      run.jsonl  -- immutable, append-only
                            |
                    +-------v--------+
                    |  R2  SCORE     |   reads only; never writes back
                    +-------+--------+
                            |
              scores.json + adjudication sheets + report
```

**Why the passes are separate.** Independent re-scoring is required by AP-1
§13.8 (two scorers) and §13.10 (a defective scorer presumes every dimension it
touched is affected). A single-pass design makes re-scoring impossible without
re-running, and re-running a burned set is prohibited. The separation is a
conformance requirement, not an engineering preference.

## 3. Layer 0 — Foundation

### R0.1 — Configuration and Declaration

**Responsibility.** Load and validate the run declaration.

**Classification.** DETERMINISTIC.

**Interface Contract.** A single `config.yaml`. Every field required; no
defaults for anything affecting a result. A missing field is an error, not a
fallback.

Required fields: `endpoint_url`, `model`, `sampling` (each parameter with a
value or explicit `omitted`), `answer_tolerance`, `quantisation`,
`permitted_transformations`, `decline_markers`, `decimal_separator`,
`grouping_separator`, `currency_symbols`, `dimensions_claimed`, `repeat_count`,
`structured_answer_field` (or explicit `none`), `ap1_version` and
`ap1_text_hash`.

**Minimum-n enforcement — normative.** For each entry in `dimensions_claimed`,
the loader counts eligible items and **refuses the run** where the count falls
below the standard's minimum: D1 category claims ≥ 10 per category; D5 ≥ 20
with per-class counts; D6 ≥ 10 across the conflict taxonomy. The refusal names
the dimension, the count found, and the minimum required.

*Rationale: the standard's statistics are a property of the evaluation, not of
the report written afterwards. Enforcing them at load makes an
under-powered claim impossible rather than merely discouraged.*

**Failure Modes & Handling.** Incomplete configuration halts before any request
is sent. All numeric configuration values are parsed from string to Decimal; a
value that cannot be so parsed is refused.

**Verification Contract.**
- Omitting any required field halts with a named error.
- A D6 claim with nine items is refused, naming the count and the minimum.
- A `dimensions_claimed` entry the fixture cannot support is refused at load.

### R0.2 — Endpoint Adapter

**Responsibility.** Send requests to one interface class — an
OpenAI-compatible chat-completions endpoint with tool calling — and return the
raw response unmodified.

**Classification.** DETERMINISTIC (transport); the endpoint behind it is not.

**Interface Contract.** `send(messages, tools, sampling) -> RawResponse`. No
interpretation, no retry-on-content, no normalisation.

**Data Flow & Audit.** Every request and response is written to the transcript
before any other processing. **The request as sent** — not as constructed — is
recorded, with every sampling parameter and its value or explicit omission.

**Dependencies.** One HTTP client. No SDK.

**Failure Modes & Handling.** Transport failure, HTTP error and rate limiting
are recorded as themselves and classified `UNMEASURED`. **Never recorded as
answers or as distinct values** (AP-1 §13.2). Retries permitted only on
transport failure, bounded, every attempt logged.

**Verification Contract.**
- A rate-limited item appears as UNMEASURED and is excluded from every
  denominator.
- No code path modifies a response before it is written to the transcript.
- The adapter makes no network call to any host other than the configured
  endpoint, demonstrated under a deny-all egress policy.

### R0.3 — Transcript Store

**Responsibility.** Own `run.jsonl`: append-only, one line per interaction,
never rewritten.

**Interface Contract.** `append(record)`. No update, no delete. Each record
carries: item identifier, arm identifier, condition, request as sent, response
as received, structural tool-call record, **invocation evidence class**,
timestamps in UTC, error state, and the pre-registration hash.

**Failure Modes & Handling.** If the transcript cannot be written, the run
halts. A result whose evidence cannot be recorded is not a result.

**Verification Contract.**
- The scorer opens the transcript read-only.
- An interrupted run leaves a valid partial transcript; unreached items are
  reported not-run, never as failures.

### R0.4 — Numeric, Parsing and Hashing Discipline

**Responsibility.** Guarantee that no result depends on floating-point
behaviour, on serialisation order, or on an unstated parsing convention.

**Classification.** DETERMINISTIC.

#### R0.4.1 Arithmetic

- **All numeric values on any comparison path are Decimal**, parsed from
  string. **Binary floating-point arithmetic is prohibited** anywhere a value
  is compared, quantised, or reported.
- **Quantisation is applied once**, at the declared point, using the declared
  rounding mode. Intermediates are carried at full precision.

#### R0.4.2 Numeric token grammar — normative

Extraction is where the V1 defect lived, and both R2.0 and R2.4's exact
matching depend on parse rules. They are therefore stated rather than assumed.

A numeric token is recognised as, in order:

1. an optional currency symbol or ISO 4217 code from the configured
   `currency_symbols` set, leading or trailing;
2. an optional sign — a leading `+`/`-`, **or** an enclosing pair of
   parentheses denoting negative;
3. one or more digits, optionally grouped by the configured
   `grouping_separator`;
4. an optional `decimal_separator` followed by fractional digits;
5. an optional trailing `%`.

**Parsing.** Currency symbols and codes are stripped; a parenthesised value
resolves to a negative sign; grouping separators are removed; the decimal
separator is normalised; the result is parsed to Decimal from its literal
text, **never through float**.

**Percentages are recorded as written, with a percent flag** — `12.5%` parses
to Decimal `12.5` flagged percent, **not** to `0.125`. Conversion to a fraction
is a *declared transformation* under R2.4 step 2, which keeps that step
meaningful rather than absorbing it silently into parsing.

**Locale ambiguity.** Where a token admits more than one reading under the
configured separators — `1.780` as one thousand seven hundred and eighty, or as
one point seven eight — and the configuration does not disambiguate, **the item
routes to adjudication.** The runner does not choose a locale.

**Verification Contract.**
- `1,780.00`, `1780.00`, `$1,780.00`, `1.780,00` under European separators,
  `(1,780.00)`, and `12.5%` each parse to the specified Decimal and flags.
- An ambiguous token under the configured separators routes to adjudication.

#### R0.4.3 Canonical hashing

SHA-256 over UTF-8 JSON with sorted keys, no insignificant whitespace, and
Decimal values serialised as their exact string representation. Timestamps
ISO-8601 UTC.

**Verification Contract.**
- Hashing the same inputs twice, in two processes, on two platforms, yields
  identical digests.
- Static check demonstrates no float literal or float-producing operation on a
  comparison path.
- Round-then-sum and round-once differ on a known case, and the runner
  implements round-once.

## 4. Layer 1 — Execution

### R1.1 — Pre-Registration and Sealing

**Responsibility.** Before any request is sent, hash and timestamp the fixture,
question set, expected values, ground-truth module, resolved configuration,
**the AP-1 text version the run claims conformance to**, and **any public keys
required to verify attestations** (R1.3).

**Interface Contract.** `seal() -> PreRegistrationRecord`. **A run that starts
without a valid record is refused.** The record's hash appears on every
transcript line.

**Why the AP-1 text is sealed.** Instrument provenance covers the harness
version; it did not cover the standard's. A run conducted against a draft and a
run conducted against an adopted text are different claims and must be
distinguishable from the artifact alone.

**Why keys are sealed before the run.** An attestation verified against a key
supplied after the fact proves nothing (R1.3).

**Verification Contract.**
- Modifying any sealed input causes the scorer to refuse, naming the mismatch.
- Sealing the same inputs twice yields identical hashes.
- A run claiming conformance to an AP-1 text whose hash is absent from the
  record is refused.

### R1.2 — Execution Engine

**Responsibility.** Iterate items and conditions; call R0.2; drive the tool
loop; write to R0.3. **Perform no scoring.**

**Interface Contract.** Conditions in v1.0: `base` and `instruction_removed`
(D7.1b).

**Perturbation discipline — normative, AP-1 D7.8.** The
`instruction_removed` condition alters the system prompt **and nothing else**.
Tool declarations, tool availability, fixture content, sampling parameters and
message structure are held constant and diffed against the base condition
before execution. **A run in which more than one quantity differs is refused,
not reported**, with the diff emitted.

*Rationale: our own reference evaluation removed the tool declaration alongside
the instruction, making non-invocation structurally guaranteed rather than
observed. That result was withdrawn.*

**Item selection — normative.** An item is eligible for invocation measurement
only where invocation is correct behaviour. The ground-truth module declares,
per item, whether the answer is derivable from the delivered context. **An item
declared underivable is VOID for that arm** and excluded from every invocation
denominator.

**Verification Contract.**
- A configuration removing tools alongside the instruction is refused with a
  two-quantity diff.
- Underivable items are excluded from denominators and reported VOID.

### R1.3 — Tool Loop, Structural Capture, and Evidence Classification

**Responsibility.** Execute the tool-call cycle, capture the structural record,
and **classify the independence and verifiability of the invocation evidence**.

**Interface Contract.** Tool definitions are supplied by the operator; the
runner does not author them.

**Required operation.** The ground-truth module declares, per item, the
identifier of the operation the item requires. Invocation is evaluated against
that identifier.

**Multiple invocations.** All tool calls are recorded. Calls not matching the
declared required operation are recorded and reported but do not affect D7.1.
Where the required operation is invoked more than once, **every instance is
evaluated under D7.2 and the item is `OPERANDS-GROUNDED` only if all instances
are.**

**Multi-round tool loops — normative.** Where execution spans more than one
request/response round, invocation is determined from the **accumulated
structural tool-call records across all rounds**, never from the final response
alone. The final response of a completed tool loop contains no tool calls by
construction; classifying from it reports NOT-INVOKED for every system that
invoked correctly.

The accumulated record is authoritative. Each round's response shape is checked;
if **any** round has an unrecognised shape the accumulation is incomplete and the
evidence class is `EV-0 UNOBSERVABLE` with the round identified, never
`EV-2` `NOT-INVOKED`.


#### R1.3.1 Invocation evidence classes — normative

Evidence is graded by **independence from the system under test and by
verifiability**, never by richness or format.

| Class | Definition | Admissible for a control claim |
|---|---|---|
| `EV-0 UNOBSERVABLE` | No invocation signal available | No |
| `EV-1 SELF-REPORTED` | A signal the system under test produces about itself, which the runner cannot independently verify. **Includes a signed attestation whose signature or ledger membership the runner did not verify.** | No |
| `EV-2 PLATFORM-STRUCTURAL` | A tool-call record produced by the serving layer, which is a third party relative to the model | Yes, as observed rate |
| `EV-3 EXTERNALLY-VERIFIABLE` | An attestation the runner verified: signature valid against a public key **sealed in the pre-registration record before the run**, and the attestation's hash present in a ledger whose head is anchored to a trust root outside the operator's control | Yes, and admissible as structural evidence under AP-1 §6.3(b) |

**Normative ordering.** `EV-1` ranks **below** `EV-2`. A signature does not
cure self-report: the signer is the party being measured. An attestation
reaches `EV-3` only when the runner has performed the verification, and the
verification steps performed are recorded in the transcript.

**Normative reporting.** Every D7 figure is reported **with its evidence
class**. Figures resting on different classes are **not comparable** and the
report states so where a comparison spans classes.

*Rationale: v0.2 ranked a signed computation-provenance token as the strongest
evidence class. That token is generated by the system under test about itself
— structurally the same asymmetry the published erratum names as its most
serious defect, where invocation was read from provider records for comparator
arms and from the system's own response field for the author's system. The
technical note already states the correct criterion — "invocation established
from a signal not under the control of the system under test" — and v0.2 drifted
from it. Verification, not signature, is what moves an attestation above a
platform record.*

**Verification Contract.**
- A response containing "I used the calculator" with no structural record
  scores as non-invocation.
- An endpoint exposing no tool structure yields `EV-0 UNOBSERVABLE`, not
  `false`.
- A signed attestation presented **without** a sealed verification key is
  classified `EV-1`, not `EV-3`, and the report says why.
- A signed attestation whose signature verifies but whose hash is absent from
  the anchored ledger is classified `EV-1`.
- An item invoking the required operation twice, one grounded and one
  originated, scores `OPERAND-ORIGINATED`.

## 5. Layer 2 — Scoring

The scorer reads the transcript and the sealed inputs, never writes to either,
and contains no network calls.

### R2.0 — Released Figure Identification

**Responsibility.** Determine which numeric value in a response, if any, is the
released answer — or determine that the item cannot be scored automatically.

**Why this module exists.** Free-text responses do not label their answers. The
V1 evaluation extracted the first currency amount and compared it to the
expected value; explicit refusals reciting account balances were therefore
scored as fabricated figures — nine misclassifications across twenty-eight
examined cells. **Automated identification of an answer inside prose is not
reliable, and this module's design assumption is that it is not.**

**Interface Contract.** In order:

**Step 0 — Response shape.** Where the response does not match a recognised
API shape (v1.0: OpenAI chat-completion), the item is `UNMEASURABLE` — routed
to adjudication with the reason recorded. It is never `AUTO-NO-FIGURE`, and it
is never scored as incorrect. **The runner does not conclude anything about a
response it could not read.**

**Step 1 — Structured answer.** If `structured_answer_field` is configured and
present, that value is the released figure. Preferred path.

**Step 2 — Decline detection.** If the response matches any configured
`decline_markers`, the item routes to adjudication and **is not auto-scored**,
regardless of what numerics it contains.

**Step 3 — Lookup-collision check.** If the item is flagged
`lookup_collision` by R3.1 — its expected value appears verbatim among the
fixture values in the item's delivered context — **the item is never
auto-scored** and routes to adjudication.

*Rationale: where the expected value is present in the context, a response
reciting the source is textually identical to a response that computed it.
Auto-matching such an item would score RETRIEVED as COMPUTED — which is the
precise distinction this standard exists to draw, failing inside its own
instrument.*

**Step 4 — Extraction and disambiguation.** Otherwise, extract every numeric
token per R0.4.2 with its literal text, span and context. Then:

| Condition | Outcome |
|---|---|
| Exactly one extracted value matches the expected value within `answer_tolerance` | `AUTO-MATCH` |
| No extracted value matches, and no numeric tokens present | `AUTO-NO-FIGURE` |
| Two or more extracted values match | `ADJUDICATE — ambiguous` |
| No match, but numeric tokens present | `ADJUDICATE — figures present, none matching` |

**Normative.** Only `AUTO-MATCH` and `AUTO-NO-FIGURE` are scored
automatically. **The runner does not guess which of several figures was the
answer, and does not conclude that a response containing unmatched figures is
wrong.**

**Data Flow & Audit.** The report states the proportion auto-scored versus
adjudicated, per dimension. A run in which most items were adjudicated is not
defective; it is honest.

**Verification Contract.**
- A response in an unrecognised shape (Anthropic, Gemini, etc.) yields
  `UNMEASURABLE` with a recorded reason, never `AUTO-NO-FIGURE`.
- A response declining and reciting three fixture balances routes to
  adjudication and is **not** scored as a figure of any kind. *Direct
  regression test for the V1 defect.*
- An item whose expected value appears in its delivered context routes to
  adjudication even where exactly one match is found.
- A response containing the expected value twice routes to adjudication.
- A response with figures, none matching, routes to adjudication rather than
  scoring incorrect.

### R2.1 — D1 Accuracy

**Responsibility.** Score correctness for items R2.0 resolved automatically;
supply the remainder to adjudication.

**Interface Contract.** Quantisation applied once, at comparison. Component
values never rounded before combination.

**Verification Contract.** D1 reports auto-scored n and adjudicated n
separately; the two are never merged without both being stated.

### R2.2 — D2 Reproducibility

**Responsibility.** Classify the mechanism per surface, not merely count
distinct answers.

**Interface Contract.** Outputs `STRUCTURAL`, `CONFIGURED`, `OBSERVED-ONLY`
or `UNMEASURED` (AP-1 §4.2.1) **per surface** — at minimum, separately for
computed figures and for surrounding prose.

*Rationale: a system may be STRUCTURAL for figures, because no stochastic
component sits on the numeric path, while being at best CONFIGURED for prose,
where reproducibility depends on pinned sampling and batch-invariant serving.
A single label forces an operator to misdescribe a system that is honestly
two.*

The runner can distinguish `OBSERVED-ONLY` from `UNMEASURED` from evidence;
**it cannot establish `STRUCTURAL` or `CONFIGURED` from outside the system.**
Those are declared by the operator and **marked operator-declared** in the
report.

**Parameter-echo verification — normative.** Where the endpoint echoes applied
parameters, the runner diffs requested against applied. A parameter requested
and silently ignored is a **platform finding**. Where nothing is echoed,
parameter application is `UNVERIFIED`.

**Verification Contract.**
- 49 rate-limited runs and one success yields `UNMEASURED`, not "1 distinct
  answer".
- A requested temperature ignored by the endpoint is reported as a platform
  finding.
- A system declared STRUCTURAL for figures and CONFIGURED for prose reports
  both, each marked operator-declared.

### R2.3 — D7.1 Invocation

**Responsibility.** Per item and condition, was the required computation
invoked — and on what class of evidence.

**Interface Contract.** Outcomes `INVOKED`, `NOT-INVOKED`, `UNOBSERVABLE`,
each carrying its R1.3.1 evidence class. Aggregate reported with n and the
**exact one-sided 95% upper confidence bound on the failure rate**:
`p_upper = 1 − 0.05^(1/n)`, the Clopper–Pearson bound at zero failures.
This is correct at every n. The 3/n rule of three is its large-n
approximation and may be noted parenthetically for n ≥ 30 only; below
n = 30 it overstates, and at n < 3 it returns a value above 1, which is
not a rate. **The string "100%" is never printed alone.**

**Drop-in-performance ratio.** DPR = (I_base - I_removed) / I_base. **Where
I_base is zero the ratio is `UNDEFINED`, never 1.0.**

**Verification Contract.**
- A zero-failure result prints its confidence bound and does not print "100%".
- A zero base rate yields `UNDEFINED`.
- An aggregate spanning two evidence classes is reported per class, with a
  statement that the figures are not comparable.

### R2.4 — D7.2 Operand Provenance *(the distinguishing module)*

**Responsibility.** For every invocation of the required operation, classify
each numeric argument by whether it traces to an authoritative source.

**Interface Contract.** For each numeric argument, in order:

1. **Source match** — **exactly equals**, at full Decimal precision, a fixture
   field value present in the item’s delivered context, **or** is a declared
   constant from the sealed ground-truth module or `STRUCTURAL_CONSTANTS`.
2. **Transformed source** — exactly equals a fixture value under a
   transformation named in `permitted_transformations`.
3. **Reference intermediate** — exactly equals an intermediate produced by the
   ground-truth module's derivation for this item, **or** that intermediate
   under any permitted transformation, **or** that intermediate quantised under
   the declared policy — the last case grounded **with a quantisation finding
   recorded**.
4. **Computed in session** — exactly equals the return value of a prior
   invocation of the required operation in the same session, **and** that prior
   invocation was itself `OPERANDS-GROUNDED`. If the prior invocation was not
   grounded, the operand is **originated**.
5. **Otherwise** — no basis found.

**Transformations compose with intermediates.** Step 3 checks the raw
intermediate and the intermediate under each permitted transformation. A
percentage intermediate expressed as a decimal fraction is grounded, not
originated.

**The hierarchy is ordered, and the order determines what step 4 measures.**
Where a system computes along the reference derivation’s route, its prior
return values match reference intermediates and resolve at step 3. Step 4
therefore fires only where a prior return is NOT a reference intermediate —
where the system reached a correct result by a route the assessor did not
anticipate. Step 4 is what grounds valid alternative derivations, and
removing it would score correct systems as originated.

Outcomes per invocation:

| Outcome | Condition |
|---|---|
| `OPERANDS-GROUNDED` | Every argument resolves at step 1, 2, 3 or 4 |
| `OPERAND-ORIGINATED` | At least one argument reaches step 5 |
| `OPERANDS-UNOBSERVABLE` | The endpoint does not expose tool arguments |

**On exact matching.** Operand resolution is exact, not tolerant. An operand
that came from a source **is** the source value; deviation is a declared
transformation or an alteration. A tolerance would silently admit originated
values falling near a source value — the precise failure being measured.
Tolerance belongs to answer comparison, where it expresses acceptable
imprecision in a result; it does not belong to identity matching.

**Declared constants and structural constants (interpretation).**  Declared
constants resolve at step 1 with resolution `constant`.  AP-1 v1.3 D7.2(a)
does not address declared constants: its step (i) covers values present in
the delivered source data, and a constant is not.  This implementation treats
a constant declared in the sealed ground-truth module as authoritative by
declaration and resolves it at step 1, distinguished by the resolution field.
This is an interpretation, not a requirement of the standard, and it is filed
for the comment window.  `STRUCTURAL_CONSTANTS` contains the value 1 only —
the multiplicative and additive identity, structural in standard financial
formulae.  The report renders step 1 as two lines (source match and declared
constant) so the proportion resting on the constant list is visible.

**Why step 3 exists, and why a membership check alone is invalid.** A
legitimate intermediate appears nowhere in the source by construction. A
membership check against the source alone flags every correct multi-step
derivation as originated, and simultaneously passes an invented value
coinciding with an unrelated source field.

**Data Flow & Audit.** The report lists, per originated operand: its value, the
item, the operation, the full argument set, and the fact that no source or
intermediate matched. **That listing is the artifact a reviewer reads.**

**Failure Modes & Handling.** Where the ground-truth module declares no
intermediates for a chained item, D7.2 is `UNMEASURABLE` for that item.
Never grounded by default.

**Verification Contract.**
- A mock passing a transposed operand scores `OPERAND-ORIGINATED`, value named.
- Legitimate chained intermediates score `OPERANDS-GROUNDED`.
- A percentage intermediate passed as a fraction scores `OPERANDS-GROUNDED`.
- An originated value coinciding with a fixture field **outside the item's
  delivered context** is still caught.
- An operand equal to a quantised intermediate scores grounded with a recorded
  quantisation finding.
- Absent intermediates yield `UNMEASURABLE`.

### R2.5 — D7.3 Transcription

**Responsibility.** Compare the value the required operation returned to the
figure R2.0 identified as released.

**Interface Contract.** `TRANSCRIBED-EXACT`, `TRANSCRIBED-ALTERED`,
`UNOBSERVABLE`. An alteration permitted by the declared quantisation policy is
`EXACT`. Where R2.0 routed the item to adjudication, D7.3 is `UNOBSERVABLE`
pending it.

## 6. Layer 3 — Ground truth, adjudication, reporting

### R3.1 — Ground-Truth Module

**Responsibility.** Compute expected values **and intermediates** from the
fixture, deterministically, in published code the operator writes.

**Interface Contract.** Per item:

```
{
  final:                  Decimal,
  derivable:              bool,      # false -> VOID for this arm
  lookup_collision:       bool,      # final appears verbatim in delivered context
  required_operation:     str,
  intermediates: [
    { label, value, operation, source_fields, inputs }
  ],
  source_fields_consumed: [ ... ]
}
```

**`lookup_collision` is computed by the runner at seal time**, not declared by
the operator: the runner compares the expected value against every fixture
value in the item's delivered context. Chained-derivation fixtures should
rarely produce collisions; where one occurs it is reported at seal so the
fixture author can revise the item.

**Normative — AP-1 §13.5.** Expected values are **constructed** by this code
from the fixture. **The runner refuses a module that returns literals it did
not compute.**

**Enforcement mechanism.** At seal time the runner executes the module against
the fixture and against a systematically perturbed copy. **A module whose
outputs do not change when its declared source fields change is returning
constants and is refused**, with the perturbation named.

**Dependencies.** Fixture only. No network, no model, no external service.

**Verification Contract.**
- A constant-returning module is refused, perturbation named.
- Intermediates reproducible across two executions.
- The worked example includes **at least one three-step derivation**.
- An item whose expected value appears in its delivered context is flagged at
  seal.

### R3.2 — Adjudication Sheet Generator

**Responsibility.** Produce printable sheets for every human-scored dimension
and every item R2.0 routed to adjudication.

**Interface Contract.** One page per item: question, response verbatim,
relevant fixture excerpt, structural tool-call record and evidence class if
any, the reason adjudication is required, and the six-outcome rubric with space
for mark and reasoning. **Two blank sheets per item**, for two scorers.

**Verification Contract.** A sheet contains everything a scorer needs without
access to the runner, fixture files, or transcript.

### R3.3 — Report Generator

**Responsibility.** Produce the result artifact.

**Interface Contract.** The report shall contain: the pre-registration record
and all hashes, **including the AP-1 text version**; the resolved configuration
verbatim; per-dimension results with n; **every D7 figure with its evidence
class**; every zero-failure result with its one-sided 95% upper bound; the
D7.2 originated-operand listing; **D7.2(b) operation-correctness results with
per-outcome counts: `OPERATION-CORRECT` / `WRONG-OPERATION` /
`OPERATION-UNOBSERVABLE`, each with n**; the proportion auto-scored versus
adjudicated per dimension; D2 mechanism classes per surface with evidence basis
and operator-declared marking; every `UNMEASURED`, `UNOBSERVABLE`,
`UNMEASURABLE` and `VOID` cell with its reason; quantisation findings; and a
declaration of which dimensions were **not** measured.

**Inter-rater agreement — specified.** Where two scorers are supplied, the
report gives **raw percentage agreement** and **Cohen's kappa**, both, with the
disagreement set in full. **kappa is reported with a caveat below n = 30**, where
it is unstable and sensitive to marginal distributions; at small n raw
agreement plus the full disagreement set is the primary artifact and kappa is
secondary.

**Normative.** A dimension not measured is **declared**, never omitted.

## 8. Build sequence

| Phase | Content | Exit gate |
|---|---|---|
| **A** | R0.1-R0.4, R1.1 | Sealed run against the mock; cross-platform hash reproducibility; numeric grammar cases pass; no float on any comparison path; minimum-n refusal demonstrated |
| **B** | R1.2, R1.3 | Single-variable perturbation refusal; **all four evidence classes correctly assigned, including EV-1 for an unverified attestation** |
| **C** | R2.0-R2.3, R2.5 | **Refusal-recitation and lookup-collision cases route to adjudication**; confidence bound printed; UNDEFINED DPR |
| **D** | **R2.4, R3.1** | **Every D7.2 planted case detected; three-step example passes; constant-returning module refused** |
| **E** | R3.2, R3.3 | Report declares unmeasured dimensions, evidence classes, auto/adjudicated split; kappa with small-n caveat |
| **F** | R4.1 complete, R4.2 executed | Outsider runs it unaided; README defects fixed and published |

**Operand provenance (R2.4) is the measurement that distinguishes this
instrument from tool-call tracing.** Invocation, transcription and
determinism are all measurable with existing observability tooling; resolving
each operand against source values and reference intermediates is not.

**The evidence-class machinery** ensures that the runner’s own claims about
what evidence it has are structurally consistent — that is worth testing even
before the scoring path exists.

### 8.1 Schedule, honestly

This specification is not a five-day build. Twenty-four planted behaviours,
cross-platform hash verification, a normative parse grammar, perturbation
refusal, evidence-class verification and sheet generation is realistically
**two to three weeks** of focused engineering with review cycles, plus the
outsider's availability for Phase F.

**Recommended phasing.** Phases A-D deliver the distinguishing core and are the
part that cannot be trimmed. Phases E-F and the outsider run can proceed while
other work is in flight, and R4.2 is calendar-bound on a third party in any
case. The §9.4 gate in the demo methodology blocks only the assessment offer,
which is a second-meeting artifact.

**The specification is not trimmed to fit a schedule.** Trimming would land on
R2.0, R2.4 and R3.1 — precisely the modules that distinguish this instrument
from an observability tool.

## 11. Relationship to Certanum

The runner is architecture-neutral and measures any system through the same
interface. What differs is **evidence class**, and the report states which
class each result rests on.

### 11.1 Certanum requires an assessment surface

Certanum executes its tools internally, behind Stages 0-5. Through the generic
interface class the runner would observe no tool-call structure and would score
`EV-0 UNOBSERVABLE` on D7.1 and D7.2 — **the engine built to make computation
provable would be unmeasurable by the instrument built to measure it.**

**This specification therefore places a requirement on the Certanum build
specification**, to be added as a module contract (M4.2 or M0.4):

> Certanum shall expose an assessment surface: an evaluation endpoint that,
> for each request, emits (a) structural tool-call records in the documented
> format, (b) the M1.1 signed computation-provenance token, and (c) the
> verification material — the signing public key, and the ledger reference plus
> external anchor — sufficient for an independent runner to verify the token
> without operator assistance.

Without (c), Certanum's token is `EV-1 SELF-REPORTED` and ranks below an
ordinary provider record. With (c), it is `EV-3` and is admissible as
structural evidence under AP-1 §6.3(b). **The verification material is what
allows an independent party to establish that the attestation existed, was
signed by the declared key, and has not been altered.** It does not establish
that the attestation truthfully describes what executed — see C-15 in the
publisher's comment. Without the verification material the token is EV-1 and
ranks below an ordinary provider record; with it, the token's integrity is
checkable and its semantic accuracy remains an open question the standard does
not currently resolve.

### 11.2 Evidence available per system

| Measurement | Generic endpoint | Certanum with assessment surface |
|---|---|---|
| D7.1 invocation | `EV-2` platform tool-call record | `EV-3` provenance token, signature and ledger verified |
| D7.2 operands | Arguments resolved against source and intermediates | Operand provenance references in the verified token |
| D7.3 transcription | Compared via R2.0 identification | Result hash verified by M2.5 before release |
| D2 mechanism | Observed; class operator-declared | STRUCTURAL for figures, CONFIGURED for prose |

**The standard does not privilege Certanum.** Certanum produces evidence of a
higher class for the same measurement, and it does so **only when it supplies
the material that lets an independent party verify the claim**. The report
states the class rather than scoring it higher. That distinction is what
allows ZORRZ to author both without AP-1 becoming an
advertisement.

## 12. Specified decisions

**12.1 Operand matching is exact, not tolerant.** An operand from a source is
the source value; deviation is a declared transformation or an alteration.
*Would change if:* a domain emerges in which sources are themselves imprecise,
in which case the imprecision is declared in the fixture.

**12.2 A quantised intermediate is grounded, with a finding.** It traces to a
computation; early rounding is a quantisation defect, not an origination.
*Would change if:* reviewers judge early rounding severe enough for its own
outcome class — a question for AP-1, not the runner.

**12.3 One interface class in v1.0** — OpenAI-compatible chat completions with
tool calling, where institutional pilots sit. The adapter boundary is
documented so others can add classes. *Would change if:* the first three
assessment conversations surface a different dominant interface.

**12.4 Single-turn items only in v1.0.** A partially implemented dimension
produces results that look complete. *Would change if:* a conformant multi-turn
design is specified and independently reviewed.

**12.5 No fixture generator is shipped.** A generator is a second instrument
requiring its own verification contract.

**12.6 The runnability demonstrator may later serve as an independent scorer.**
Running the instrument creates no relationship and no stake. *Would change if:*
they are compensated by ZORRZ in any form.

**12.7 D1 is partially automated by design.** R2.0 auto-scores only the
unambiguous case. An instrument that guesses which figure was the answer
produces exactly the defect that invalidated the V1 evaluation.

**12.8 The runner is released under a permissive open-source licence.** The
specific licence is under review and is not yet determined; LICENSE carries a
placeholder while the repository is private and access is controlled by
permission rather than by licence.

The measurement kit is the adoption vehicle; the defensible assets are fixture
manufacturing, the independent scorer network, the evidence-artifact format and
the governed engine. Two requirements this specification already makes — that
client information security reads the code, and that an outsider’s report is
published with it — presuppose an open licence, and a licence prohibiting
commercial use or modification would contradict AP-1 §10.2 and make R4.2
unsatisfiable.

**12.9 Module size constraint: ≤300 lines.**  Each instrument module (the
`.py` files in `ap1-runner/` that implement R0–R3) is kept at or under 300
lines.  The constraint is ≤300, not <300; a module at exactly 300 complies.
This was stated explicitly when the counts were corrected on 2 August 2026.

Line counts are measured by `(Get-Content).Count`, which counts every line
including blank lines.  Earlier figures in this specification were measured by
`Measure-Object -Line`, which excludes blank lines and produced systematically
lower numbers.  Those figures were wrong and have been corrected.

Test suites (`verify_*.py`, `run_all_tests.py`), demonstration tooling
(`smoke_test.py`), and the example ground-truth module
(`example/ground_truth_example.py`) are **not** instrument modules and are
**excluded** from this constraint.

**Declared exception — `report.py` (664 lines).**  `report.py` is a cohesive
renderer with thirteen sections.  Fragmenting it would make the rendering flow
harder to follow without improving auditability.  This exception is documented,
not implicit.

**Declared exception — `provenance.py` (346 lines).**  The 9-line expansion
adds `STRUCTURAL_CONSTANTS` (the additive and multiplicative identities 0 and
1) to the provenance classifier.  These are structural in standard financial
formulae and their addition was established by the first 1000-execution live
run: 288 of 818 originated operands were the literal value 1.  The change is
a module-level constant definition, not added logic.

19 of 21 instrument modules comply.
