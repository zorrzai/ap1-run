# Retiring `tests/legacy/`: every legacy check and the new tests that replace it

Generated by `tests/legacy/retirement/build_retirement.py`; edit that script, its header and
footer files, or the group maps beside it (`tests/legacy/retirement/g1-…md` to `g7-…md`), and
rebuild, rather than editing this file:

    PYTHONPATH=src python tests/legacy/retirement/build_retirement.py

The build takes an inventory of every legacy check (see below), joins it to the group maps that
step 3's groups G1–G7 wrote, adds the rows that G9 (the retirement audit) settled, and stops if a
named test does not exist in `tests/{unit,conformance,functional,inspect}/` or if a suite's count
differs from `run_all_tests.py`'s `SUITES`.

## The criteria

A legacy suite is retired (deleted, removed from `run_all_tests.py`, noted in the changelog) when:

1. **Every check is mapped** to a new test, or dropped on purpose with a reason. *Status:* 410 of
   410 checks accounted for: 347 mapped and 63 with no replacement, each with its reason; none
   pending (summary below). One is dropped. The other 62, `verify_spec.py`'s SPEC line-count
   checks, are proposed drops: the maintainer decides on them with the legacy-suite retirement,
   and until then `verify_spec.py` keeps running them.
2. **No coverage is lost**: the new tests execute every line and branch the suite did. *Status:* met
   for every suite, with no exception (section "Coverage" at the end).
3. **Strength is not lost**: on the modules the suite covers, the new tests' mutation score is at
   least the suite's. *Status:* met for every module (section "Mutation" at the end).

What still blocks deleting each suite is listed at the end ("Blockers").

## How to read the tables

- **A check** is what `run_all_tests.py` counts. `verify.py`, `verify_conformance.py` and
  `verify_spec.py` count `check()` calls, so each call is a row (a call in a loop is one row per
  pass, as the suite counts it). `test_findings_mutation.py` counts its seven helper calls. The
  other suites count test functions: one row per function.
- **line**: for a `check()` row, the line of the call in the test function (if the call is in a
  helper, the helper's line too). For a function row, the `def` line, then the line of every
  `assert`, `self.assert…` call and failing `return` in it.
- **new test(s)**: `path::name`, the path relative to `tests/`; `R:`name`` is a regression
  scenario, `tests/regression/scenarios/<name>.json`, checked against golden output by
  `tests/regression/run_regression.py`.
- **note**: the group's note, then in parentheses the group whose map the row comes from (G9: this
  audit). "Stronger" means the new test pins exact values where the legacy check tested presence or
  type; "test defect" marks a legacy check that passes for a reason other than the one it states (a
  test-infrastructure issue, not a runner defect); finding IDs (`T3-n`, `S3-…`) are pinned as
  today's behaviour, to be fixed in step 5.
- **dropped**: no new test on purpose, with the reason. **proposed drop**: no new test, with the
  reason, proposed to the maintainer and not yet decided; the legacy check still runs.
  **pending**: no mapping or proposal yet; none at present.

## Blockers to deleting the suites

- **All suites:** Marcus's approval, the gate before step 5 (the fixes).
- **`verify_spec.py`:** the maintainer's decision on its 62 checks, which this map proposes to
  drop: line counts are not behaviour, and the ≤300-line limit would go with them. If they are
  dropped, what they check, SPEC §12.9 (the limit) and the §12.10 line-count table, should go in
  the same change (with README's sentence on the limit), or they go stale unchecked. Nothing else
  blocks it.
- **`verify_hashes.py`:** `.github/workflows/hashes.yml` runs it; switch the workflow to
  `pytest tests/unit/foundation/test_numeric.py -k verify_hashes_input` (or to the whole unit
  suite) in the same change that deletes it.
- **`run_all_tests.py` and the docs:** the registry, `.github/workflows/full_suite.yml` (runs
  `run_all_tests.py`), and the docs that cite "14 offline suites" (README, SPEC, the paper's next
  revision) change with the deletion.
- **`verify_inspect.py`:** not a blocker, but note that its replacement tests in `tests/inspect/`
  need inspect-ai and skip without it, as the legacy agreement test did. CI installs `.[dev]`
  only, so in CI both skip; run them in an environment with inspect-ai (`ap1-run-inspect`).
- None of the suites is blocked by a missing test, a coverage gap or a lower mutation score.
